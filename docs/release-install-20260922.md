# 发布安装链故障记录（2026-09-22）

## 实际故障

原始 `.9` mrpack 内是旧 LT2 compat.14、旧 Thunderbolt beta.3 compat.2，
不是 ZIP 内已经夹带新旧两份。随后最小发布只更新了二进制附件和 Pages 清单，
并未重建客户端包。新导入 `.9` 后运行公开更新器，才产生了新旧两份并存。

旧包没有 packwiz 安装历史。上游更新器验证或下载当前目标后报告成功，但无法从
不存在的旧记录知道导入包内哪些文件被替代。已有安装也有一个相关边界：当改名后的
新目标已存在且哈希正确，validateExistingFile 会提前更新 cachedLocation，随后的
alreadyUpToDate 路径直接返回，原旧路径可能失去清理机会。

上游不是完全没有改名清理：正常下载分支会移除旧位置。因此不能用“所有改名都会
遗留旧文件”概括，也不能只在事后保护用户修改过的旧 JAR——需要在调用上游前检查。

来源：[packwiz-installer 0.5.14 DownloadTask](https://github.com/packwiz/packwiz-installer/blob/v0.5.14/src/main/kotlin/link/infra/packwiz/installer/DownloadTask.kt)、
[UpdateManager](https://github.com/packwiz/packwiz-installer/blob/v0.5.14/src/main/kotlin/link/infra/packwiz/installer/UpdateManager.kt)。

## 为什么会“看似成功”

- assets 上传、packwiz 清单发布、mrpack 重建是三个独立步骤，之前缺少共同验收门禁。
- 原发布脚本在 git push 后直接发布附件，没有等待并验证 Pages 的实际文件。
- 安装成功只说明当前目标文件已处理，不说明 mods 目录只剩当前版本。
- 安装文档已经要求重命名检查，但包内并没有可执行的统一安全更新器，容易漏做。
- 原发布脚本紧接着部署生产服务器，将客户端发布与服务器部署混成一次操作。

修复目标是安装文件正确，不是依靠 Forge 选择重复模组的行为。运行时选择旧 LT2
只是本次文件错误已经影响实际加载的旁证。

## 现在的验收条件

1. 新 mrpack 下载清单精确匹配当前元数据，每个下载的字节校验通过，顶层 Forge 模组 ID 唯一。
2. 旧包导入、已存在新目标、重复运行均只保留当前版本；已知旧文件可从备份恢复。
3. 无法确认身份或已修改的旧文件在更新前或清理前明确报错，不盲删、不报成功。
4. 保存历史和快照；上游失败后恢复缺失的已验证旧文件，阻止游戏继续启动。不是全目录事务回滚。
5. options 仅作新实例预设；在线更新不管理玩家现有 options.txt，预设引用的材质包必须随包可取得。
6. 发布先校验公开 Pages 内容，再上传草稿并重下载比对，最后转正式；服务器部署单独授权执行。
7. 最小二进制发布只能报告“更新源已更新，客户端包尚未重建”，不能报告完整客户端发布完成。

## 测试边界

真实 `.9` 副本升级已确认旧 LT2/TB 被归档，99 个当前模组 JAR 校验通过，无重复 ID。
新候选包包含 110 个锁定下载（含资源包/光影）。主菜单验证使用离线测试身份，
不代表通过服务器正版登录；进服验收必须由用户使用 HMCL 正版账号完成。
