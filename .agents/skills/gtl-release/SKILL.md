# GTL 发布验收

将“发布”视为可复核的交付，而不是一次命令。当前包版本、构建提交和文件名从工作树、
元数据和实际远端读取；这里不保存某一版的“最新 JAR”名单。

## 先确定范围与工作树

1. 用 `git rev-parse --show-toplevel`、`git remote -v`、`git status --short` 确认仓库与改动。
   发布对象是 `kairan0/gregtech-leisure-pack`。有运行中配置或未审查改动时使用独立干净
   checkout；先记录所选路径、基线提交和候选提交，保护原实例。不同 checkout 不能混用清单。
2. 按本次用户授权选择范围；读取技能、检查状态、构建候选本身不授权 GitHub 上传或服务器写入。

   | 用户要求 | 必须完成的范围 | 能报告的结果 |
   | --- | --- | --- |
   | 检查是否最新／调查发布 | 只读比较实际文件与发布入口 | 各入口一致或具体差异 |
   | 本地验证／准备候选 | 构建、安装和验收副本 | 候选已验证；尚未发布 |
   | 发布（未明确缩小范围） | 本技能完整客户端流程 | 全部门禁通过后才称完整发布 |
   | 仅最小发布／只上传 JAR | 明确授权的附件、源码、元数据 | 更新源已更新；整包重建是否未完成 |
   | 部署服务器 | 另行授权的目标部署和启动验证 | 服务器部署结果，不替代客户端发布 |

3. 开始执行前完整读取仓库 `CODEX_INSTALL.md`、`scripts/export-mrpack.sh`、
   `scripts/release-check.py`、`scripts/publish.sh`，以及
   [验收与证据](references/acceptance.md)。涉及更新或部署时再读 `gtl-update.py` 与对应包装脚本。
   缺少这些门禁实现就停在“工具缺失”，不能退回直接上传或裸跑 bootstrap 的旧流程。

## 完整客户端流程：逐关执行

### A. 冻结已验收输入

- 列出本轮改动的模组、源码提交、验收结论、JAR 哈希，以及共同目标：客户端、在线清单、mrpack、服务器。
  开发目录里“时间最新”但未验收的 JAR 不自动进入发布；同名或相同内部版本号不证明内容相同。
- 核对远端默认分支和最新非草稿客户端 Release，下载其 mrpack 索引；`assets-*` 不是客户端 Release。
  已验收的新附件与旧 mrpack 不一致时，列为待修复差异，不能仅检查 `.pw.toml` 就宣布最新。
- 更新 pack 版本、锁定下载元数据和面向玩家的变更说明。附件保持不可变；更换内容使用新文件名或新 tag。
  源码归档与二进制构建对应。禁止把私有存档、账号、令牌、会话或无关本地配置加入附件。

### B. 构建和机器门禁

- 在候选 checkout 运行 `python3.11 -m unittest discover -s scripts/tests -p 'test_*.py'`。
- 准备阶段可运行 `scripts/export-mrpack.sh --preview`；审查、提交 refresh 产生的清单后，
  正式构建运行 `scripts/export-mrpack.sh`。解释器可用仓库脚本支持的 `GTL_PYTHON` 指定。
- 对生成的实际 mrpack 运行 `scripts/release-check.py`。它必须验证下载 URL、实际字节哈希、
  唯一模组 ID、无夹带 JAR、更新器和 options 资源引用；见参考中的精确调用。
  `--payload-root` 只能复用经过哈希验证的下载字节，不能把本机未发布内容填入包内。
- 记录候选提交、pack 版本、mrpack SHA-256、测试命令和原始结果。任何输入变化都使相关验收失效。

### C. 玩家安装和目标服务器验收

- 依据参考分别验证：全新导入、旧版升级、新目标已预先存在的升级、重复更新、失败保护。
  验收对象是导入／更新后的实际 `mods` 目录；每个受管模组恰好一份当前哈希 JAR。
  “Forge 能挑出一个”“主菜单能打开”“packwiz 显示成功”均不能替代该条件。
- 默认 options 只初始化新实例，已有玩家 options 不覆盖。禁止复制主实例的 mods/config 来掩盖发布缺件。
- 用候选实际安装副本启动。连接正版服务器必须使用用户授权的启动器账号，不读取令牌。
  从用户确认和对应日志验证完成登录、加载世界；离线身份、服务器列表 ping、连接按钮被点击、
  只到主菜单都不算进服成功。必要交互交给用户，当前状态保持待验收。
- 与目标服务器按 side 核对共同模组的哈希、受管配置和脚本；客户端专用项不要求服务端安装。
  服务端尚需更新时，报告差异并取得部署权限；不能为了让测试通过而擅自替换生产文件或停服。

### D. 公开交付

- 确认本次公开上传／推送权限及目标；会话中已明确授权的相同范围无需重复确认。运行已审查的仓库发布入口，保留草稿、下载比对和 Pages
  一致性门禁。当前 `scripts/publish.sh` 会重建附件：发布前必须证明其游戏载荷与 C 阶段候选相同，
  见参考，使用 `scripts/publish.sh --accepted-artifact /absolute/path/to/accepted.mrpack`；
  载荷变化则回到 C。不要以直接 `gh release upload/create` 绕过失败的入口。
- 公共 Pages 验证通过才继续：`git push` 成功不代表 Pages 已传播。只做有界重试（至多 3 次，
  每次间隔不超过 30 秒）；仍不同步则报告停在哪个阶段。保留草稿和候选，不覆盖旧正式资产。
- 重新下载用户实际会得到的 Release 附件，核对 tag、版本、源码提交和字节哈希；核对公开清单
  指向相同 JAR。对“上一正式版导入 → 公共更新源”再执行升级验收，不以本地模拟代替公开链路。
- 只有参考中的全部必需门禁 `PASS`，才能报告“完整客户端发布并验收通过”。如果远端已经写入
  但后续失败，准确报告“已上传／已公开，但验收失败”，不要伪装回滚或重复宣告完成。

## 最小发布与服务器部署的边界

- 最小发布仍要核验上传后实际下载字节和公开元数据；记录未重建的客户端版本及受影响的旧包。
  明确告知“直接下载整包仍旧，完整发布未完成”。用户已限定范围时不擅自扩成完整发布。
- 部署前精确确认目标、游戏进程状态与备份。只通过受管更新入口部署并核对最终哈希及启动日志。
  不把服务器更新隐含绑定到客户端发布；部署失败与发布失败分别报告。
- sandbox 内的 gh 网络／认证失败按工作区规则用最小宿主权限重试，不重置 GitHub 登录状态。

## 收尾格式

按参考保留证据表，最终简要给出：本次范围、候选／公开版本及提交、Release 链接、
mrpack 哈希、安装升级／正版进服／服务器部署各自结论、仍待完成的阶段。
`未运行`、`等待用户`、`失败`都不是 `PASS`。检查命令退出成功只证明该命令覆盖的门禁。
