# 验收与证据

## 执行和留证

在选定 checkout 下使用当前脚本；先读脚本确认参数。证据保留在 Git 忽略的 `dist/` 或
`compat/`，不得把含本机路径、玩家身份、地址或私有配置的原始日志自动上传。
每个结果记录执行时间、命令、退出码及证据文件；不以手填 PASS 替代执行。

```bash
python3.11 -m unittest discover -s scripts/tests -p 'test_*.py'
scripts/export-mrpack.sh
python3.11 scripts/release-check.py "dist/GregTech-Leisure-$gtl_version.mrpack"
python3.11 scripts/release-check.py "dist/GregTech-Leisure-$gtl_version.mrpack" --public
```

`gtl_version` 从本次 `pack.toml` 解析，不能直接沿用示例或历史变量。
默认 Python 版本不适用时使用已验证的 3.11+ 可执行文件。
`--public` 会比较公开 Pages 内容；候选尚未推送时预期不通过，不能提前计为通过。
上述静态门禁不证明启动、升级和进服成功，必须补齐下表的动态证据。
`--public` 必须实际从公开 URL 下载载荷，不能只验证缓存。如果所用脚本版本尚未实现，
先补实现或单独保留等价的真实网络下载与哈希证据，再计入公开交付验收。

## 完整发布的必要证据

| 门禁 | PASS 的具体证据 |
| --- | --- |
| 公开内容 | 完整 staged Git 树、packwiz 索引及实际 mrpack 通过 content_policy；逐项审查提交目的，无玩家运行数据或临时过程记录；源码公开范围和安装范围分别核验 |
| 输入身份 | 干净构建提交、pack 版本、已验收 JAR 的哈希和源码对应关系；无意外降级 |
| 导出内容 | release-check 成功记录；mrpack 索引和字节通过校验；每个顶层模组 ID 唯一 |
| 全新安装 | 仅从本次 mrpack 安装的副本，所有目标下载哈希一致，受管模组无缺少／重复／额外旧版 |
| 旧版升级 | 从上一正式 mrpack 新导入且无 packwiz.json 的副本升级；旧包已归档，新包唯一且哈希正确 |
| 已有新目标 | 保留旧 packwiz 状态且预置新目标 JAR 的副本升级；结果仍只有当前文件 |
| 幂等和失败保护 | 重复更新结果不变；损坏新包、已修改旧包、未知重复包阻止成功；失败保护回归通过 |
| 玩家预设 | 新安装取得已发布的材质包顺序／按键；已有 options 更新前后字节相同；不从主实例补缺件 |
| 启动及进服 | 该候选安装副本启动；用户经授权正版账号完成目标服务器登录与世界加载，有对应确认／日志 |
| 公开清单 | 公开 pack/index/metafile 和下载内容与发布提交及候选 JAR 一致；不是只读取本地缓存 |
| 公开整包 | 用户入口指向本轮正式客户端版本，下载附件哈希与已验证载荷匹配，tag 指向预期源码提交 |
| 公开升级 | 上一正式包经公开更新 URL 更新后，实际模组目录符合唯一当前版本条件 |
| 服务端一致 | side=both/server 按适用范围核对目标服务器文件及运行状态；client-only 差异有解释 |

仅做候选、审计或最小发布时，未授权的公开写入／部署门禁列“范围外”，并保持该任务范围的称谓；
这不允许将范围外包装成完整发布。完整发布的必需项不能用 N/A 跳过。

## 可复现的安装测试

使用独立空目录、真实 mrpack 索引、其 overrides/client-overrides 和实际下载 URL。
下载缓存可以复用，但逐文件按发布哈希校验；引擎运行库缓存单独说明。
旧实例升级使用 `update-gtl.sh`／`update-gtl.bat`，不能裸跑 Java 后凭肉眼删包充当修复。
候选尚未公开时可从候选提交提供临时本地更新源进行预验收；对外发布后补做公开 URL 验收。

用于本地 HTTP 更新源的参数会与脚本默认公开地址不同，必须在记录中写明；不能称为公共安装已通过。
副本保留旧文件列表、packwiz 状态和更新后文件哈希；若新版没有构建到公开清单，文件名正确也不算通过。

受管文件不能靠名称判断版本。读取当前 `.pw.toml`、实际下载哈希以及 JAR 的 `META-INF/mods.toml`。
新旧文件内部版本号相同依然可能是两个不同构建。历史清理依据导入清单／旧 packwiz／可信哈希记录，
只归档已确认旧文件，未知冲突停止并请求方向。

## 候选与最终附件的关联

导出 ZIP 的时间戳等容器信息可能变化；优先发布已验收的同一字节附件。
现有发布入口重建时，保留验收附件，比较两个 ZIP 中每个条目的路径和解压后 SHA-256、
下载索引及下载哈希；若只有容器信息不同，可沿用游戏行为验收并记录两个 mrpack 哈希。
任何游戏载荷、默认配置、资源包、更新脚本或下载目标变化都重新验收受影响部分。
仅 AGENTS/skill 等不进入游戏包的文件变化可解释为不影响游戏载荷，但仍核对发布源码提交。

完成草稿附件下载比对后才转正式；如发布入口不能在转正式前保证验收附件关联，
先补齐入口的该检查再发布，不用技能文字替代缺失的机器门禁。

## 失败状态和对外措辞

重试前只读检查已有 tag、草稿、附件和远端 main。复用草稿需证明其提交、附件哈希与
同一验收候选一致；不同则停止，不覆盖附件或移动 tag。若脚本不能恢复已有草稿，
先增加可验证的恢复分支，不将整段发布命令盲目重跑。每次只继续尚未完成的阶段，
公开升级验证失败也保持失败状态，不因为 Release 已经可见而改记成功。

| 实际状态 | 允许的结论 |
| --- | --- |
| 新 JAR 上传，但 mrpack 仍旧 | 最小附件发布完成，客户端整包未更新 |
| installer 退出 0，但 mods 有新旧两份 | 安装验收失败 |
| main 更新，但 Pages 仍旧 | 源码已推送，公开更新源未同步 |
| 本地能启动，公开附件未下载核验 | 本地候选通过，公开交付未验证 |
| 离线身份只到主菜单 | 启动通过，正版进服未验证 |
| 新 Release 已公开，进服失败 | 已公开但不可验收，报告具体故障和下一步；不能宣布可用 |

现有官方 Release 发布时间不会因往旧 assets tag 添加附件而变成新整包发布。
核对时间时标明时区；历史调查证据仅从本地忽略目录按需读取，不作为默认公开文档。
